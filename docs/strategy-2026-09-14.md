# LocalBar — Strategic Direction
**Session date:** 2026-09-14  
**Deciders:** Jay

---

## What LocalBar is

LocalBar is a **local LLM inference manager** for people who self-host language models on their own hardware. It manages the lifecycle of inference servers (start, stop, model selection, parameter tuning) through a menu bar app and settings window.

The target user travels a lifecycle:

1. **Experimenter (B-mode):** Actively tuning — trying different models, adjusting temperature and context length, experimenting with system prompts and profiles.
2. **Infrastructure operator (A-mode):** Once a configuration is dialled in, LocalBar becomes invisible infrastructure — servers start automatically, run quietly, and stay out of the way.

The product must serve both modes. The tray popover (A-mode) is the operational surface; the Settings window (B-mode) is the configuration surface. They are complementary, not alternatives.

## Platform strategy

### Now: macOS

The first release targets macOS. This is where Apple Silicon + mlx-lm makes local LLMs genuinely practical for power users. The Swift/SwiftUI prototype demonstrates the UX; it will be **feature-frozen** after the three critical bugs below are fixed and the remaining structural warts are resolved.

### Near-term: Linux (staged)

The rewrite targets macOS + Linux simultaneously using **Tauri** (Rust core + web frontend). Linux is a first-class platform in the rewrite, not an afterthought, because a large proportion of self-hosting power users run Linux servers.

### Future: Windows

Windows arrives via a **CLI tool first** — the Rust core is designed platform-agnostically so a Windows CLI binary requires no new platform work. A Windows GUI (Tauri on Windows) follows once the Linux GUI is stable. This allows the team to validate Windows demand without the full cost of a GUI port.

### Technology choice: Tauri

The Swift app is frozen after bug fixing. All new feature development happens in the Tauri rewrite:
- **Rust core** — platform-agnostic server lifecycle, model management, persistence, driver protocol
- **Web frontend** (React or Svelte, TBD) — shared between macOS and Linux GUI
- **CLI binary** — thin shell around the same Rust core; the Windows MVP

## Server driver architecture

### Full drivers (own process lifecycle)

Drivers that own the inference process completely — spawn, monitor, health-check, and tear down:

| Driver | Status |
|--------|--------|
| mlx-lm | In (macOS/Linux Apple Silicon) |
| Ollama | In |
| llama.cpp | In (planned) |

### Generic external driver

A driver for any server exposing an OpenAI-compatible API. Covers: LM Studio, vLLM, exllamav2, koboldcpp, and anything else that speaks the standard. LocalBar manages configuration and provides the UI surface; the server process is externally owned.

### Modality scope

**LLM-first.** This means:
- Text generation (chat, completion) — now
- Multimodal / vision LLMs (LLaVA, Qwen-VL, etc.) — now, as they are LLM endpoints with an image input
- Diffusion models, TTS, mlx-Optiq and other non-LLM modalities — future driver extensions; the architecture accommodates them, but they are not in scope for v1 or v1.1

The driver protocol (`ServerDriver`) is designed to be modality-neutral. Adding a diffusion or TTS driver later is a new driver implementation, not an architectural change.

## UX principles

### Two surfaces, one purpose

**Tray popover (A-mode):** operational. Start/stop servers, switch models, see status at a glance. Optimised for speed — one click to start, one click to stop.

**Settings window (B-mode):** configurational. Add/remove instances, tune parameters, manage profiles, browse models. Optimised for precision.

### No in-app chat panel

LocalBar does not include a chat interface. Users already have preferred frontends (Open WebUI, Continue, Cursor, custom scripts). LocalBar's job is to keep the server running and correctly configured — not to duplicate what the ecosystem already does well.

### Instance-first workflow

Users create an **instance** (server + port + model search path), then select a model within that instance. This maps to how the underlying tools work and makes the mental model concrete: "I have an mlx-lm server on port 8080; right now it's running Qwen2.5-7B."

## Monetisation

### Personal use: free

Everything a solo power user needs stays free. The primary personal-use revenue mechanism is **voluntary donations**. Gate nothing on payment that a personal user would reasonably want.

### Commercial use: licensed

Organisations using LocalBar commercially pay a licence fee. Commercial-tier features centre on team/org needs:

- Fleet management (central visibility of instances across machines)
- Team profile sync (shared parameter profiles across an org)
- Usage analytics (model usage, uptime, inference patterns)

The exact boundary between personal-free and commercial-licensed features will be determined iteratively as the product matures. The governing principle: if a feature is primarily useful to an individual, it stays free; if it primarily creates value at org scale, it's commercial.

### Open core

The core codebase (server drivers, lifecycle management, local persistence) is open source. Commercial features are in a closed extension layer.

## v1 Tauri MVP scope

The first Tauri release establishes the **core loop only**:

- Instance management (add, edit, remove)
- Server lifecycle (start, stop, adopt running)
- Model selection and switching
- Basic parameter tuning (temperature, context length, core Ollama params)
- Tray popover + Settings window (two-surface UX)
- Persistence (instances, model memory)

**Deferred to v1.1+:**
- Named profiles
- Advanced flags UI (OLLAMA_KEEP_ALIVE, --kv-cache-bits, etc.)
- Multiple model search paths UI
- Context usage display
- Modelfile baking optimisations (debounced commits)
- Linux staging / Windows CLI

## Swift app: immediate fixes before freeze

Three bugs must be fixed before the Swift app is feature-frozen. They are documented in detail in `docs/review-2026-09-14.md`.

| # | File | Issue | Fix |
|---|------|-------|-----|
| 1 | `ServerInstanceController.swift` ~L471 | `performAPIModelSwitch` creates Modelfile for wrong model | Set `config.selectedModelKey = model.key` before calling `ensureManagedModelIfNeeded()` |
| 2 | `ServerInstanceController.swift` ~L211 | Profile activation doesn't trigger Modelfile rebuild | Add `profileChanged` to the `updateConfig` trigger condition |
| 3 | `SettingsView.swift` ~L872 | Every param keystroke fires `ollama create` | Commit only on `onSubmit`, not on every char change |

Structural warts (dead `AppSettings`, duplicated `humanName()`/`paramValueString()`, ghost `CanonicalParam.systemPrompt` case) should be cleaned up at the same time but are non-blocking for freeze.
