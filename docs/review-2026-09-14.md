## Bugs

### Bug 1 — `performAPIModelSwitch` creates the Modelfile for the wrong model
**File:** `LocalBar/Services/ServerInstanceController.swift` ~L471  
**Severity:** High (silently broken Ollama param baking)

`ensureManagedModelIfNeeded()` reads `config.selectedModelKey` to derive the base tag for `ollama create`. But at the point it's called in `performAPIModelSwitch`, `config.selectedModelKey` still holds the **old** model's key — the assignment `config.selectedModelKey = model.key` happens after the switch succeeds. Result: the new model's Modelfile is never correctly built before it's warm-loaded; the old model's Modelfile gets an unnecessary rebuild.

**Fix:** Set `config.selectedModelKey = model.key` before calling `ensureManagedModelIfNeeded()`, then call `driver.switchModel`.

```swift
// Correct order:
config.selectedModelKey = model.key
await ensureManagedModelIfNeeded()
try await driver.switchModel(to: model, params: params, config: config)
currentModel = model
onConfigChanged?(config)
```

### Bug 2 — Profile activation doesn't trigger Modelfile rebuild
**File:** `LocalBar/Services/ServerInstanceController.swift` ~L211  
**Severity:** High (profile params not baked until next model switch)

`updateConfig` only calls `ensureManagedModelIfNeeded()` when `selectedModelKey` or `instanceParams` changes:

```swift
if modelKeyChanged || ollamaParamsChanged { ... }
```

Activating a profile changes `activeProfileID`, which changes the resolved params, but doesn't satisfy either condition. The Modelfile baked into Ollama will still reflect the old (pre-profile) params until the user manually switches models.

**Fix:** Add the profile ID change as a trigger condition:

```swift
let profileChanged = newConfig.activeProfileID != config.activeProfileID
if modelKeyChanged || ollamaParamsChanged || (newConfig.type == .ollama && profileChanged) {
    Task { await ensureManagedModelIfNeeded() }
}
```

### Bug 3 — Every param keystroke spawns `ollama create`
**File:** `LocalBar/UI/SettingsView.swift` ~L872  
**Severity:** Medium (excessive subprocess spawning; noisy `ollama list`)

`paramBinding`'s setter calls `commitText` on every character. `commitText` calls `controller.updateConfig`, which triggers `ensureManagedModelIfNeeded()` → a full `ollama create` subprocess. Typing "0.75" into the Temperature field fires four `ollama create` calls on an Ollama instance.

Sliders already do this correctly — they only commit `onEditingChanged: { if !editing { commitText(descriptor) } }`. TextFields and Steppers should follow the same pattern: commit only on `onSubmit` / stepper value commit, not on every character.

## Structural Warts

### 4 — `AppSettings` and `PersistenceService.saveSettings/loadSettings` are dead code
**Files:** `LocalBar/Core/DataModel.swift`, `LocalBar/Services/PersistenceService.swift`

`AppSettings.systemNotificationsEnabled` is never loaded or injected anywhere. `GeneralTab` uses `@AppStorage("localbar.notificationsEnabled")` and `notify()` reads the same UserDefaults key directly. The `PersistenceService` methods `loadSettings()` / `saveSettings()` are defined but never called. This creates a false impression that there's a proper settings persistence layer, and the `AppSettings` struct is a dead type.

**Recommendation:** Either wire it up (load in `bootstrap()`, inject via environment, read from it in `notify()`) or delete the struct and the two persistence methods. The `@AppStorage` approach is fine and simpler for a single boolean.

### 5 — `humanName()` and `paramValueString()` are duplicated verbatim
**File:** `LocalBar/UI/SettingsView.swift` ~L930 and ~L1939

`InstanceDetailPanel` and `ProfileDetailPanel` each contain private implementations of these two functions (`profileHumanName`/`profileValueString` in the latter). They're byte-for-byte identical. These belong as extensions on `CanonicalParam` and `ParamValue` in `DataModel.swift`, accessible to all UI code without duplication.

### 6 — `CanonicalParam.systemPrompt` is a ghost enum case
**File:** `LocalBar/Core/ServerDriver.swift` ~L123

`CanonicalParam` has a `.systemPrompt` case, but the system prompt is never stored in `ParamValues.values` — it lives in the separate `ParamValues.systemPrompt: String?` property. Code that tries `values[.systemPrompt] = .string(...)` would silently store something that's never read as a system prompt. The case exists only so the `humanName()` switches are exhaustive.

**Recommendation:** Either remove the case (update `humanName()` switches) and add a comment on `ParamValues` explaining the separate property, or add a `// Never stored in values[] — use ParamValues.systemPrompt` doc comment on the case.

### 7 — `MLXLMDriver.listModels` returns spurious and duplicate HF cache entries
**File:** `LocalBar/Drivers/MLXLMDriver.swift` ~L146

The HF hub cache structure is:
```
models--org--name/
  snapshots/
    <hash>/          ← actual model directory (has config.json)
      config.json
  blobs/
```

The recursive enumerator finds `config.json` inside `snapshots/<hash>/` and treats it as a model — correct. But it may also find intermediate directories if they happen to contain a config. More practically, with multiple snapshots the same model appears once per snapshot hash. The `displayName` (last path component) will be a 40-char hash string, not a human-readable name.

**Recommendation:** After finding a directory with `config.json`, check whether its parent is named `snapshots` and grandparent follows the `models--*` pattern; if so, derive the display name from the grandparent directory. Skip non-latest snapshots by preferring the path referenced by `refs/main` symlink when present.

## Feature Gaps (existing schema, no UI)

### 8 — Advanced flags have no UI
`flagSchema` is fully defined for both drivers — `OLLAMA_KEEP_ALIVE`, `OLLAMA_MAX_LOADED_MODELS`, `--kv-cache-bits`, `--trust-remote-code`, startup timeout, etc. — but `advancedFlags` is only ever written by… nothing. There is no UI surface for it. The schema is being computed and returned but the data never flows in from the user.

### 9 — Multiple model search paths have no UI
`modelSearchPaths` is `[String]` on `ServerInstanceConfig`, but `AddInstanceSheet` only captures a single path via `modelSearchPath` (`@AppStorage`). Users with models on external drives or spread across directories can't configure additional paths.

### 10 — `contextUsage` is always nil for both drivers
Both `MLXLMDriver.contextUsage` and `OllamaDriver.contextUsage` return `nil`. The "Context" row in the Controls panel never appears. For mlx-lm, usage stats are available in streaming response chunks (`usage` field); for Ollama, `/api/ps` returns the loaded context size but not current fill. Neither is currently wired up.

## Smaller Observations

- **`ServersTab.task` refreshes models for every controller on every Settings window open.** For users with many instances this fires N parallel network/disk scans. A per-controller `refreshedAt` timestamp with a staleness window (e.g. 30 s) would avoid the repeated work.

- **`InstanceDetailPanel.portOverride` is not reset after a successful retry.** If a port-conflict error is resolved and a new error appears later, the port field may still show the last user-typed value rather than the config's actual port.

- **`OllamaDriver.listModels` does not parse model metadata** (quantization, param count, capabilities). Ollama's `/api/tags` response includes `size` (used) but not architecture info. `/api/show` has it — a background fetch per model at scan time, or on first selection, would populate the metadata columns that currently show `—` for all Ollama models.

## Not Findings

- The `CanonicalParam: CodingKey` conformance is intentional and correct — it lets `[CanonicalParam: ParamValue]` round-trip as a JSON object with string keys.
- The `nonisolated(unsafe) var capturedStderr` annotation is correct given the documented write-before-read ordering via process termination sequencing.
- The `EWMA` in `ModelMemory.estimatedRestartDuration` stores samples newest-first but iterates oldest-to-newest; this is correct as documented in the comment.
